小游戏：注册与合规

FakeHappy 开发文档的一部分。索引在 开发文档首页。

7. 注册小游戏

实现 MiniGame 并注册进来，就自动获得：出现在大厅选择 UI、出现在 OP 场控面板、 参与者自动被可见性隔离、自动豁免大厅保护、掉线时自动 quit、跨节点排队。

@Override
public void onEnable() {
    HappyApi api = Happy.api();
    api.games().register(this, new MySpleefGame(api));
    // onDisable 不用手动注销 —— 框架监听 PluginDisableEvent 会自动清理
}

descriptor 里的元数据是大厅 UI 和跨服排队的依据，务必填全：

GameDescriptor.builder("spleef", text.parse("<aqua>雪球战"))
        .description(text.parse("<gray>把对手脚下的雪挖穿"))
        .icon(new ItemStack(Material.SNOW_BLOCK))
        .iconSprite("<sprite:gui:icon/checkmark>")
        .players(2, 16)
        .category("pvp")
        .crossServer(true)        // 参与跨节点排队
        .isolateVisibility(true)  // 开局时与场外玩家互相隐藏
        .stage(GameStage.BETA)    // 开发阶段，决定合规检查有多严（不填默认内测）
        .partyMode(PartyMode.FOUR_BY_N)  // 编队形态，见「组队」。单人游戏也要显式写 SOLO
        .sigma(2.0)               // 货币差距系数，见「奖励与结算」。规范要求它有书面记录
        .build();

后三项是规范要求的，不填不会拦你注册，但注册那一刻的合规报告会逐条列出来（见本文「小游戏」一节）。

接口调用要求

  1. 玩家进出走 GameRegistry，不要直接调 MiniGame 上的对应方法。

    你要做的事 走这个 不要直接调
    加入 games().join(player, game) MiniGame.join
    加入指定那一局 games().joinRoom(player, game, roomId) MiniGame.joinRoom
    开始旁观 games().spectate(player, game) MiniGame.spectate
    退出（参与和旁观都是它） games().quit(uuid) MiniGame.quit

    注册表靠这几个方法维护 UUID -> MiniGame 反向索引，并顺带处理可见性隔离。 绕过去会让索引和实际状态对不上，表现是「大厅保护把正在打游戏的人拦下了」、 「他掉线了但局里还留着一个幽灵」、「“在不在游戏里”的占位符是 false」。

  2. 状态变化走 GameRegistry.setState，不要只改自己的字段。 否则大厅 UI 和跨服房间信息不会更新。

  3. players() 要便宜（大厅 UI 每秒问很多次），返回不可变视图或副本。

quit(UUID) 收的是 UUID 不是 Player —— 掉线时框架也会调它，那时玩家已经离线了。

活动与自动开局

小游戏每次推进自动开局倒计时之前检查 Happy.api().eventModeHere()。为 true 时暂停自动开局，并取消已经开始的自动倒计时，等待管理员 / 场控明确开始。 查询的是当前活动目标状态，serverRole() 只是固定配置：MINIGAME 子服也会临时成为活动目标，不能只用 ServerRole.EVENT 判断。 该查询同步读取框架缓存，活动结束或转移到其他子服后返回 false，游戏可以恢复平常的自动开局规则。

抽奖发起节点、外置开奖与场控接管见 活动接管。小游戏只读取当前活动模式，不自行修改共享活动状态。

可见性隔离与旁观

isolateVisibility(true) 是框架替你做的，你不用碰 hidePlayer：

  • 参与者与场外玩家互相隐藏。注意这跟玩家自己的「隐藏玩家」开关无关 —— 挡视野的那个人自己是不会去点隐藏的，挂在开关上就等于没有这个功能。
  • 同一个游戏的参与者互相看得见，别的游戏的看不见。

旁观走 games().spectate(...) 的话，可见性按规范 8.1 处理，而且是不对称的：

看得见
旁观者看场内玩家 ✔（不然就没得看了）
场内玩家看旁观者 ✘ 规范 8.1「观战者对玩家不可见、不可干扰」
大厅里的人看旁观者 ✘
旁观者看同一局的其他旁观者 ✔
旁观者看别的局 ✘

这一套要框架的可见性模块启用（大厅子服默认开着）。模块关着时框架会在 控制台警告一次，不会静默失效 —— 游戏跑得好好的、只是场外能挡视野， 没人会往「模块没开」上想。

独占子服的小游戏用 isolateVisibility(false)，自己拿旁观者模式之类的手段处理。

已经有自己一套观战实现的

spectate(...) 默认会替你做两件事：强制切成原版 SPECTATOR，以及把他对局内玩家隐藏。 自己写了观战（自己的可见性服务、导播位、自由镜头）的游戏两套一起上只会打架 —— 谁后跑谁赢，表现成「观战偶尔抽风」。

.spectatorTakeover(false)   // 视角和可见性归我，观战索引还是登记

关键在于「还是登记」：spectatingGameOf 照样认得他，所以聊天隔离（10.2）、 语音那边的观战自动闭麦这些只看索引的功能不受影响。 从前想保住自己那套观战就只能整个不用框架的 spectate(...)， 连带把这些也一起丢了 —— 这个开关就是为了把两件事拆开。

代价是规范 8.1 的视角与不可见两条从「框架负责」变成你自查： 合规报告里会多出 spectate.self-managed 这条必须项，做到了在 compliance() 里 done("spectate.self-managed")。

大厅保护的豁免

大厅保护（挖不了方块、打不了人、不掉血不掉饿）对小游戏参与者自动不生效， 判据是 isInProgressGame —— 也就是局已经开起来了：

  • 还在等开局的人照样受保护。那时候他就站在大厅里晃，跟别人没区别。
  • PVP 要求双方在同一局里。参与者打场外的人、或者打另一局里的人，照样被拦。
  • 你的游戏在自己的世界里跑（不在大厅保护覆盖的世界里）的话， 本来就没有大厅保护，这一段可以不用管。

爆炸不在豁免范围内：BlockExplodeEvent / EntityExplodeEvent 认不出「这是谁点的」， 框架不去猜。要在大厅世界里炸方块的游戏，把场地放到单独的世界。

同时开好几局的游戏

MiniGame 代表的是这个子服上的这个游戏，不是「一局」。同时跑多局的 （比如每支队伍一块地皮的玩法）覆写 rooms()：

@Override
public Collection<GameRoom> rooms() {
    return matches.all().stream()
            .map(m -> new GameRoom(String.valueOf(m.plotIndex()),
                    mapState(m.state()), m.size(), MAX_PARTY, 1))
            .toList();
}

不覆写的话默认实现返回一个「整体」房间，单局制的游戏不用管。

覆写之后配套要做的：

  • state() 返回聚合状态（有任何一局在跑就是 RUNNING）
  • joinRoom(player, roomId) 把人放进指定那一局 —— 跨服排队是按房间分配的， 塞进另一局就把队友拆散了，而那正是跨服排队最该保证的事。 人已经在这个游戏的另一局里时框架也会调它（跨服排队把他分到了别的房间），实现里要能换局
  • roomOf(uuid) 说出每个人（参与者和旁观者）在哪一局（合规项 room.player-room，必须）。 框架里凡是「同一局」的判断都靠它：
    • 局内聊天：全局 / 观战 / 队伍频道只发给同一局的人（格式沿用这台子服平时的聊天格式；全局 / 队伍 / 观战频道前面各挂一个小图标）。不覆写的话一号房的话会发到二号房去
    • sameGame / isInProgressGame：大厅保护按他那一局开没开算 —— 别的房间开打了， 等人这一局的人照样受保护；PVP 要求两人在同一局
    • 可见性隔离（isolateVisibility(true)）：场景按局分开，两局的人互相看不见
    • 语音分房：一局一间，teamOf 里不用再自己编局号
    • 带队加入：队长落在哪一局，本服的队友就进哪一局
    • 「所在房间」「游戏状态」占位符（给他那一局的状态）
  • 场控逐局操作：覆写带 roomId 的 forceStart / forceStop / pause / isPaused / reset。 场控面板「小游戏 → 逐局操作」里点某一局就走这几个；远程场控的 subject 写 游戏id#房间id。 不覆写的话退回整个游戏的那个方法
  • roomState(roomId) 默认在 rooms() 里找，大厅保护每个事件都会问，最好覆写成查表
  • rooms() 要便宜：框架每 3 秒调它做跨服上报

自己在局与局之间挪人（玩家在游戏里点「换房间」）时，先 games().quit 再 games().joinRoom， 或者直接 games().joinRoom 到新房间 —— 隔离场景要跟着换，绕过注册表的话他还留在旧那一局的场景里。

框架会自动把这些房间上报到跨服层（带过期时间），代理据此分配玩家； 子服被 kill -9 时房间信息会自己过期，不会在大厅里留下幽灵记录。

7.5 战绩与跨服偏好

DataService data = api.data();
if (!data.isAvailable()) { /* 没配数据库 —— 但下面的调用照样能写，只是不落盘 */ }

// 一局打完，累加战绩。异步，不阻塞
data.record(playerId, "spleef", StatDelta.builder()
        .play().win().kills(3).score(1200).playtime(elapsedMs).build());

// 排行榜（回调在异步线程！）
data.leaderboard("spleef", DataService.StatField.SCORE, 10)
        .thenAccept(top -> { /* ... */ });

// 跨服偏好：玩家在大厅关掉的开关，切到小游戏服还是关着的
data.setPrefBool(player, "hide-players", true);
boolean hidden = data.prefBool(player, "hide-players", false);   // 同步读缓存

战绩使用相对增量，避免跨服同时读改写覆盖更新。普通战绩写入不返回 Future，失败记录在后台日志。

prefCached 是同步读，只查本机内存（玩家进服时已预热）—— 事件处理里用它， 不要在事件里等 Future。

偏好是「全框架共用」的那一层，键空间是平的（hide-players、voice-uid 这种）。 你自己游戏的数据不要往这儿放 —— 撞键的那天没有任何东西会报错， 两边各自把对方的值覆盖掉。存自己的东西用下面的 store()。

存自己的数据：PlayerStore

战绩（局数、胜场、分数、排行榜）上面 record() 已经记过了，别重复写。 只有你的游戏才懂的东西 —— 个人最高纪录、赛季进度、今天领没领 —— 走这个：

PlayerStore store = api.data().store(descriptor().id());   // 命名空间 = 你的游戏 id

store.setInt(uuid, "best", 128);                           // 永不过期
store.set(uuid, "played.today", "1", Reset.DAILY);         // 到每日重置时刻自动消失
store.set(uuid, "cooldown", "1", Duration.ofMinutes(5));   // 5 分钟后自动消失

int best = store.getInt(uuid, "best", 0);                  // 内存读，主线程随便调
boolean played = store.has(uuid, "played.today");
long resetAt = store.expiresAt(uuid, "played.today");      // 显示「距离重置还有多久」

键是你的。 底下会加上 你的命名空间: 前缀，所以你的 best 和别人的 best 不是同一个键；你也写不到框架自己的键上（想写都构造不出那个键名）。

过期不是定时任务。 Reset.DAILY 落的是一个过期时间戳，读的时候比一下 —— 十几台子服各自判断、结论必然一致，不会「重置跑了两遍」。

别自己写 now + 24h。 那样每个玩家的重置时刻都不一样，23:59 打完的人第二天 一整天都是旧值，而且客服没法回答「我什么时候能再来」。Reset.DAILY 用的是 全服同一条线，几点由服务端配置说了算。

边界：命名空间 ≤ 20（小写字母/数字/_/-），键名 ≤ 36，值 ≤ 255 字符。 不合规的键直接抛 IllegalArgumentException，不截断 —— 这类东西全是写死的常量， 第一次跑就会炸出来。超过 255 字符说明你该用自己的表了，这里不是放存档的地方。

没有「按我的键排序」：要排行榜请用 record() + leaderboard()， 那是建了索引的列；在一个文本列上排序是会花钱的。

存的值也能作为占位符挂到 Tab 列表 / 计分板上，具体写法问服主。

把外部账号绑在偏好上

偏好也是「MC 账号 ↔ 外部账号」这类绑定的落脚点（比如把 MC 账号绑到语音账号，就存在 voice-uid 这样的键上）。这种用法多出三个需求，API 都给了：

// 判重：这个外部账号是不是已经绑给别人了。【必须用这个，不要用自己在内存里攒的反查表】
data.playerByPref("voice-uid", uid)
        .whenComplete((owner, err) -> {
            if (err != null)      { /* 不知道 —— 当成「可能已被占用」，不要放行 */ }
            else if (owner.isPresent() && !owner.get().equals(playerId)) { /* 已被占 */ }
            else                  { data.setPref(playerId, "voice-uid", uid); }
        });

// 管理界面：这个键全网有哪些人设过（按最近更新排，最多 500 条）
data.prefsByKey("voice-uid", 200).thenAccept(map -> { /* UUID -> uid */ });

// 别的子服改了某个玩家的偏好，把自己那份缓存丢掉
var sub = data.onPrefChanged((playerId, key) -> { if ("voice-uid".equals(key)) forget(playerId); });
// 插件卸载时 sub.cancel()

多子服查询要求：

  • 自己攒的 uid → 玩家反查表只认识本服在线的人。 拿它判重，「那个人正好在别的子服」 时会静默放行，同一个外部账号被两个 MC 号绑走。
  • playerByPref 是本接口里唯一一个查询失败时 future 以异常完成的读方法。 把「数据库读不到」当成「没人占用」，等于在数据库抖一下的那一瞬间放行一次重复绑定。
  • 偏好本来没有失效通知，因为改它的人就是玩家自己。管理界面打破了这个前提 —— OP 改一个不在本服的玩家时，那台子服会一直拿着旧值直到玩家重新进服。

偏好按键建了索引，前两个查询都不扫全表。 但 prefsByKey 仍然是管理路径：翻页时按需取，不要开机拉一份全量缓存自己维护失效 —— 那是在给一份本来就有权威来源的数据造第二份事实。

7.8 规范自检：注册时那份合规报告

register 的那一刻，框架会照《小游戏制作规范》把你的游戏过一遍， 把还缺什么打到控制台：

[spec] spleef (公测) 22/35 必须项，2 项应当未做，4 项待人工，缺 10 项必须（当前是公测，仅提示）。
       游戏内管理面板 → 小游戏 → 合规 看明细

内测和公测阶段只报告缺项。正式版 stage(GameStage.RELEASE) 缺少必须项时，默认拒绝注册。 服主可以临时关掉这项强制检查作为应急放行，日志会明确记录；恢复后应重新检查。

游戏内：管理面板 → 选中你的游戏 → 规范合规 按钮，tooltip 里是缺失清单， 点一下重新检查并把完整明细打到控制台。

三种检查方式，刻意不混着报

框架能做到什么 报告里显示
AUTO 反射看有没有覆写、descriptor 字段填没填、房间有没有类型 结论可信
DECLARED 什么都验不了，只看你在 GameCompliance 里怎么说 「已声明」≠ 已验证
MANUAL 美术原创度、文案侵权、Tab 排版好不好看 只负责列出来提醒验收的人

混在一起报一个「通过率」的话，验收的人会以为框架已经替他看过了 —— 而框架其实只看得到「你有没有写 pause() 这个方法」，看不到「你的暂停有没有真的冻住实体」。

声明你做了什么

框架验不了的项靠你自己声明。不声明 = 没做，这是有意的： 默认「已实现」的话，一个从来没读过规范的人注册进来会显示满分，那这套检查就没意义了。

@Override
public GameCompliance compliance() {
    return GameCompliance.builder()
            .done("flow.back-to-hub", "flow.settlement", "econ.custom-no-reward")
            .notApplicable("midjoin", "一局 90 秒，中途进来没意义")
            .notApplicable("reconnect", "单局太短，重连窗口比一局还长")
            .build();
}
  • ID 见 SpecCatalog（flow.* / party.* / room.* / ctrl.* / spectate* / ui.* / econ.* / art.*）。 写错的 ID 会被单独列出来提醒，不会静默忽略 —— 否则一个手滑的拼写会让你以为声明过了。
  • notApplicable 必须给理由，理由会原样进报告给验收的人看。
  • 「必须」项也能声明不适用，但要写真实理由：报告和管理面板里会标成「必须项，开发者声明不适用：理由」给服主看。
  • 形态上无从谈起的项框架自己会跳过：5.3 那条「m×2 两队空位不足时的提示」对 4×n 游戏 不会挂在报告里。报告一旦永远不可能全绿，就没人会认真看了。

常见自动检查项

descriptor 上这三行是 AUTO 检测，填了当场变绿：

.stage(GameStage.BETA)          // 本身不是检查项，但它决定检查有多严（不填默认内测）
.partyMode(PartyMode.M_BY_2)    // party.mode
.sigma(2.0)                     // econ.sigma —— 规范 12.2.6 要求 σ 有书面记录，这就是那份记录

加上覆写 pause(boolean)（ctrl.pause，规范第七章的必须项）、 支持旁观就覆写 spectate(Player)、用 api.ui().board(...) 建计分板 （ui.tab-footer / ui.scoreboard）。

rooms() 会在检查时被调一次 —— 它本来就要求便宜。刚注册时通常一局都没开， 房间相关的项在「没有房间」时按通过处理：那不代表实现对，只代表现在无从判断，等有局了再看。

7.9 语音分房

服务器上有个可选拓展会自动把同一局 / 同一队的人拖进同一个语音频道， 散场再放回大厅。它只读框架已有的东西：

  • MiniGame.teamOf(uuid) —— 他在局内的哪一队
  • GameRegistry.gameOf(uuid) —— 他在哪个小游戏里
  • PartyService.partyOf(uuid) —— 他在哪支全服队伍里
  • GamePlayerJoinEvent / GamePlayerQuitEvent / GameStateChangeEvent

只要你按本章正常注册了小游戏，语音分房就已经对你生效了。 不需要你调任何 API，也不需要判断这个拓展装没装。

有队伍的游戏记得覆写 teamOf —— 你本来就要为队伍文字频道写它（10.2）， 语音是同一份事实的另一个用途。不写的话，同一局的敌我双方只要没组队就会落进同一个 语音频道，对手听得见你报点。

人人都是对手的局别分语音：单人竞技按「这一局」分一间的话，全场对手在同一个频道里。覆写 MiniGame.autoVoice(uuid)，这种局里的人返回 false，框架就不拖他们（同一个游戏里组队的局照常分）。

开打之后再分：默认进了这一局就拉进语音频道，等人、倒计时的时候也拉。队伍要开局才定的游戏 在 descriptor 里声明 .voiceAfterStart(true)：状态到 RUNNING 之前不拖人（多局制看 roomState）， 开局那一刻按队伍一次拉到位，省掉「先进本局频道、再进队伍频道」那一次拖动。

多局制的游戏覆写了 roomOf 就自动「一局一间」（没有队伍的按局分，有队伍的按局 + 队分）， teamOf 返回普通的队名就行。没覆写 roomOf 的老写法是把局号编进 teamOf （比如返回 地图/队名），分组按整个字符串走，两张图的红队自然是两个频道 —— 那样没有队伍概念的多局制游戏只能分到「游戏」这一层。

分组口径框架推不出来：自己托管

teamOf 表达不了的分组（观战者按阵营分开、死了的人留在原队伍频道、赛后合并成一间）， 可以自己算好交进来。入口是注册在 ServicesManager 里的 OopzVoiceApi：

// 接口在 fakehappy-api 里，不用加依赖；语音拓展可能比你晚加载，别缓存「没装」
var rsp = getServer().getServicesManager().getRegistration(OopzVoiceApi.class);
OopzVoiceApi voice = rsp == null ? null : rsp.getProvider();   // 没装拓展就是 null

// 自己的对账循环里，每拍声明一次「现在谁该和谁在一起」
if (voice != null && voice.available()) {
    voice.submitGroup("league:room7:red", "7 号房 红队", redUuids);
    voice.submitGroup("league:room7:blue", "7 号房 蓝队", blueUuids);
}
voice.releaseGroup("league:room7:red");        // 散场

是声明式的，不是命令式的。 submitGroup 说的是「这一拍这个分组该有这些人」—— 同一个 key 反复提交只更新成员，不会重复建频道；名单里少了谁，那个人下一拍被送回大厅。 所以正确写法是定时全量提交，不是在每个「玩家换队」事件里各调一次： 后者漏一个事件就留下一个错位的人，而且永远自己好不了。

被你点名的人自动分房那一轮就不碰了，所以不需要再声明 voiceManaged(false)。

拓展是可选的：getRegistration 返回 null（没装）和 available() 返回 false （装了但语音平台连不上 / 没配好）两种情况你都得照常能跑。语音是加分项， 不能变成故障点。

查某个玩家在不在语音里

VoiceState s = OopzVoiceApi.find().map(v -> v.voiceState(uuid)).orElse(VoiceState.UNKNOWN);
if (s.inVoice()) { /* 在语音里：s.channelName()；在你交的分组里时 s.groupKey() 是那个 key */ }
else if (!s.known()) { /* 说不准：拓展没连上、数据太旧、他不在这台子服 —— 别当成「不在」 */ }

读的是拓展的内存缓存，任意线程调、不发请求。数据每 2～15 秒刷新一次（s.checkedAt() 是查到的时间）。 只查本服的玩家；别的子服的人多半是 UNKNOWN。只要个布尔就用 isInVoice(uuid)（说不准也是 false）。

自己已经有一套语音方案

descriptor 里声明一句，框架就完全不碰这局里的人：

GameDescriptor.builder("my-game", name)
        .voiceManaged(false)        // 语音归我自己管
        ...

别让两套同时拖人。 你的方案按队把人放进 A 频道，框架下一拍按它的口径 把人拖去 B，你的下一拍再拖回来 —— 玩家会被来回拽，而两边的日志都显示自己做对了。 声明 false 之后，开频道、拖人、散场拖回大厅这三件事框架一件都不做。

声明在 descriptor 而不是各子服的语音配置里，是因为那种名单换台机器就得再维护一份， 漏了也不报错，只会表现成「这个游戏的语音偶尔抽风」。

12. 让小游戏脱离 FakeHappy 也能跑

同一份代码既要跑在装了 FakeHappy 的服务器上、又要跑在没装的服务器上时，用下面这套「软依赖三件套」。 只在装了 FakeHappy 的服务器上跑的话不用这么麻烦，depend: [FakeHappy] 直接硬依赖就行。

软依赖三件套

bridge/HappyBridge.java    接口。零 FakeHappy 引用，可以被自由加载
bridge/HappyBackend.java   实现。满是 maybe_c.happy.api.*
bridge/YourGame.java       MiniGame 实现。同样只在插件存在时才加载

关键在于接口本身不能碰 FakeHappy 的任何类型。FakeHappy 是 provided 依赖， 编译时在、运行时不一定在；接口里漏一个引用，没装 FakeHappy 的服务器就会在 类加载那一刻抛 NoClassDefFoundError，而且抛在哪取决于 JVM 什么时候决定加载它 —— 通常是「某个玩家走进了某个房间」这种毫无头绪的时机。

static HappyBridge create(Plugin plugin, ...) {
    if (plugin.getServer().getPluginManager().getPlugin("FakeHappy") == null) {
        return ABSENT;                       // 空实现，每个方法什么都不做
    }
    try {
        return new HappyBackend(plugin, ...);  // 这一行才会触发类加载
    } catch (Throwable t) {                    // Throwable：版本对不上会抛 NoSuchMethodError
        plugin.getLogger().warning("[FakeHappy] 接入失败，按未安装处理: " + t);
        return ABSENT;
    }
}

验一下有没有做对：编出来之后跑

javap -c -p -cp target/classes com.你的包.bridge.YourBridge | grep -c maybe_c/happy

接口那个类必须是 0；只有实现类（HappyBackend、YourGame）里该有引用。
