6. UI：Dialog 与箱子共用一套按钮

同一 MenuButton 可用于箱子界面和 Dialog，交互逻辑共用。

MenuButton start = MenuButton.builder(text.parse("<green>开始游戏"))
        .tooltip(text.parse("<gray>人数够了就能开"))
        .icon(new ItemStack(Material.LIME_CONCRETE))
        .visibleIf(p -> p.hasPermission("mygame.admin"))
        .enabledIf(p -> game.players().size() >= 2)
        .disabledReason("人数不足")
        .onClick(ctx -> game.forceStart(ctx.player()))
        .build();

三种菜单：

UiService ui = api.ui();

// 箱子：所有客户端都能看，保底形态
ui.chest(this, title, 3).set(11, start).fillEmpty(filler).build().open(player);

// Dialog：能放真正的输入控件（文本框 / 开关 / 滑条），要 1.21.6+
ui.dialog(this, title)
  .input(DialogInput.bool("pvp", label).initial(true).build())
  .button(save)
  .build().open(player);

// 自适应：支持就画 Dialog，否则退回箱子。用不了输入控件
ui.adaptive(this, title).button(start).withBackButton().build().open(player);

⚠ 管理类按钮的权限必须挂在 visibleIf / enabledIf 上

不能只靠「打开这个菜单的那条命令有权限」。 Dialog 的按钮是靠客户端回一个 custom click 包触发的，identifier 形如 fakehappy:m/<菜单号>/<按钮号> —— 菜单号是自增小整数、按钮号 0 起，几百个包就能枚举完，而且不需要先打开菜单。 回包里的 DialogResponseView（所有输入框的值）也完全来自客户端。

框架这边已经补了一道：MenuHost.onCustomClick 会先判发包的人是不是这个菜单的 观看者。但服务端唯一会校验的业务门就是按钮自己的 visibleIf / enabledIf （DialogMenuImpl.handleClick 只看这两个，都不设时一律放行）。所以：

.button(MenuButton.builder(text.parse("<ok>执行"))
        .visibleIf(p -> p.hasPermission("fakehappy.admin"))
        .enabledIf(p -> p.hasPermission("fakehappy.admin"))
        .onClick(ctx -> { ... })
        .build())

漏掉的代价是实打实的：奖励档位编辑器的「保存」能写入任意 commands， 而那些命令随后由框架以控制台身份执行。

⚠ 菜单要建一次长期复用，不要每次打开都新建

每 build() 一次就在框架里登记一份，开十次漏十份。内容会变的用动态求值：

// 内容随时间变（人数、倒计时）
.dynamic(11, () -> MenuButton.builder(...).build())

// 内容随观看者变（每个 OP 各自选中的那个游戏）
.dynamic(11, viewer -> MenuButton.builder(...).build())

// Dialog 输入框的初始值 —— 打开那一刻才读配置
.input(viewer -> DialogInput.bool("pvp", label).initial(cfg.pvp()).build())

最后那条尤其重要：Dialog 没有可靠的关闭事件（玩家按 ESC 时服务端收不到任何包）， 所以「每次打开新建一个 DialogMenu」建出来的那些永远等不到 dispose。 不用 input(Function) 的话，编辑界面就只能显示建菜单那一刻的旧值 —— OP 改完保存、再打开看到的还是旧值，会以为没保存成功。

调试信息里的 menus= / dialogButtons= 持续增长不回落就是漏了。

框架已经替你处理好的

  • 点击 / 拖拽全部取消，物品拿不走塞不进
  • 玩家退出 / 传送 / 死亡时自动摘除观看者
  • 插件卸载 / 服务器关闭时关掉所有界面，不会把玩家卡在死界面里
  • 导航栈：子菜单的返回按钮直接写 ctx::back
  • 按观看者逐个求值 visibleIf / enabledIf —— 同一个菜单，OP 看到 12 个按钮、助管看到 4 个

open vs openWhenFree

方法 用在哪
open(player) 玩家主动触发（点按钮、敲命令）。立即打开
openWhenFree(player) 服务端主动弹窗（进服提示、活动通知）。等玩家手头的界面关掉再开

主动弹窗一定要用 openWhenFree：玩家可能正在填资源包确认框，硬塞过去会把它顶掉， 直接导致他进不了服。

闭包引用

按钮回调里的闭包不要捕获 Player / 实体 / 世界对象，只捕获 UUID 或不可变数据。 闭包会随菜单存活，捕获对象可能延长其生命周期。

6.5 小游戏计分板：GameBoard

规范第九章对首尾三处有硬性格式要求：Tab 底部 ==游戏名称==、记分板顶部游戏名、 记分板底部的服务器地址。这三处不开放给你设置 —— 你只给中间内容，首尾框架按规范拼。 框架设置固定格式，调用方提供中间内容。

GameBoard board = api.ui().board(plugin, game)   // 拥有者插件 + 你的 MiniGame
        .lines(viewer -> List.of(
                text.parse("<gray>地图 <white>" + map.name()),
                text.parse("<gray>剩余 <yellow>" + fmt(remainSec)),
                Component.empty(),
                text.parse("<gray>你的击杀 <red>" + kills(viewer))))
        .autoRefresh(20)          // tick。有人在看才跑，没人看开销为零
        .build();

board.show(player);               // 幂等，重复调没事
board.refresh();                  // 数据变了想立刻重绘（设了 autoRefresh 就不用调）

内容函数按观看者求值，所以「你的击杀」「你的队伍」这类逐人内容是天然支持的； 不随人变的用 lines(Supplier)。

使用要求

  • autoRefresh(20) 就够。倒计时每秒变一次，给 1 是每 tick 给每个观看者重发一遍包 —— 一百人的服就是每秒两千个包。
  • 总行数 15（含框架加的首尾）、单行 32 字符。超了框架照常显示，只在控制台警告一次。 规范 9.2 这两条是「应当」不是「必须」，硬截断会让人看到半截字还不知道为什么。
  • 不用手动 dispose。插件卸载 / 服务器关闭时框架会把它创建的计分板全部 dispose。

Tab 底部那行默认一起设，被别的东西占了才 tabFooter(false) —— 关掉要在合规声明里说明。

合规检查的范围

ui.tab-footer 和 ui.scoreboard 平时是「需声明」（框架看不到你画了什么）， 调用 api.ui().board(...) 后，这两项按框架提供的格式记录 PASS。这只确认格式路径，仍需检查实际客户端渲染。 自行绘制计分板时由人工验收。

地图类游戏真把计分板当画布用了的，在 descriptor 里 scoreboardExempt(true)， 检查不再要求这两项，验收时须确认玩法确实占用了计分板。
