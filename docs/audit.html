资产审计来源

旧的经济/奖励 API 继续自动留下后台流水。需要让 OP 按插件、操作者和对局精确检索时，使用新增的 AuditContext 重载；这些内容不会作为玩家消息发送。

import maybe_c.happy.api.audit.AuditContext;
import maybe_c.happy.api.reward.RewardBundle;

var context = AuditContext.plugin(plugin.getName(), "match-win")
        .withActor("SYSTEM")
        .withReference("match:" + matchId)
        .withMetadata("{\"rank\":1}");

Happy.api().rewards().grant(playerId, new RewardBundle(100, 30, 1), "match-win", context)
        .thenAccept(receipt -> {
            // 以 granted()/skipped() 为准，不能把请求的 bundle 当成已到账。
        });

Happy.api().economy().withdraw(playerId, price, "shop-buy",
        AuditContext.plugin(plugin.getName(), "shop-buy")
                .withActor(playerId.toString()).withReference("order:" + orderId));

source 最多 128 字符，actor 128，reason 256，referenceId 128，metadata 8192；过长值截断。metadata 可以保存 JSON 或备注，不要包含密码、令牌等秘密。显式 reason 参数作为本次流水原因。

在进入异步任务之前创建上下文，操作者/对局信息由发起方保存。referenceId 仅用于关联，不会阻止重复发奖；拓展仍须自行保证结算或订单不会重复执行。上下文字段来自调用方，不能用来代替权限判断。

新重载需要新版 core。不要把 fakehappy-api 打进拓展 jar，继续使用 provided。自有数据库中的数值与流水一起提交；日志失败会返回未成功状态。奖励中的货币、经验和积分可能部分成功，应处理实际回执。普通玩家不需要查看后台流水，查询与保留策略由运维管理。
