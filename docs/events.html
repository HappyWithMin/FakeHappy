活动 API 1.4.6

只想自己办抽奖、让 FakeHappy 管「谁能进目标子服」的，用 子服准入锁，不需要接管。

名单外的人进不去目标子服：活动处于报名或进行中时，目标子服上的 FakeHappy 在玩家登录时拒绝名单外的人（他留在原来的服并看到提示）； submitDraw / replaceRoster 写进名单的人立刻能进。开奖后还待在目标子服上的名单外玩家会被送回主大厅。 有活动豁免权限的人和活动管理员不受限。拦截在子服登录这一步，不在代理；目标子服必须装 FakeHappy。

依赖 maybe_c:fakehappy-api:1.4.6，使用 provided / compileOnly，plugin.yml 加 depend: [FakeHappy]。JDK 25。API 由同版 core 提供，不要把 API 打进拓展 jar。可以直接从公开 Maven 仓库解析，连不上时用 SDK 的 libs。

接口

方法 用途
current() / roster() / guaranteedSignups() 读取当前活动、名字名单和必中报名
claimTakeover(Plugin, Duration) 获取全网控制租约；失败返回 null
renewTakeover / releaseTakeover 修改续约期限、释放自己的租约
open / update / end 创建、修改、结束活动
signup / withdraw 按 UUID 报名、取消报名
candidates(expected) / rosterWithIds(expected) 读取候选资格、权重和 UUID 名单
replaceRoster 替换本场名单，写入真实 UUID；不改长期必中规则
submitDraw 校验并持久化外接开奖结果，更新原名单及准入资格
transfer / transferReceipt(requestId) 传送名单成员、查询逐人回执
subscribe(Plugin, listener) 监听 OPENED / UPDATED / ENDED，返回可关闭订阅
EventLottery.draw 独立纯算法，不写活动、不发奖励

业务写入返回 CompletableFuture<ActionResult>。调用处使用主线程；回调可能在 IO 线程完成，操作 Bukkit UI 时切回主线程。读取 API 时重新调用 Happy.api().events()，不要跨模块重建保存旧实例。

RequestContext 必须使用真实在线 Player 或 Bukkit 控制台；管理操作要求活动管理权限，玩家只能自行报名/取消。插件安装本身属于服务器信任边界，传入的操作者字段不是对外鉴权系统。

租约

EventApi events = Happy.api().events();
events.claimTakeover(this, Duration.ofSeconds(30)).thenAccept(lease -> {
    if (lease == null) getLogger().warning("活动控制权获取失败");
    else this.lease = lease;
});

期限 5–300 秒，插件启用期间由框架自动续约。插件停用时释放；网络断开、期限到期或模块重建后重新获取。expiresAt 是申请时的快照，授权以服务端当前租约为准。

全网租约校验 owner、节点、token 和 generation。其他节点的内置活动写入被拒；旧任务即便经历接管再释放，也不能用原代际提交。活动状态、报名、名单和预设在提交时原子检查租约与完整输入快照，不依赖缓存判断。

已持久确认的开奖决定属于恢复任务，权重更新可能在租约释放后完成；它不会重新抽奖。经济、积分和管理员的独立玩家偏好编辑不由活动租约控制。开奖前会重新读取权重，并在保存决定时检查权重仍未变化。

旧 claimTakeover(String) / releaseTakeover(String) 保留兼容，名字必须对应已启用的插件，会同步访问跨服层。新插件用异步重载。

开场与修改

var request = new EventApi.RequestContext(UUID.randomUUID().toString(), operator);
var settings = new EventApi.Settings(
    "抽奖活动", 16, "小游戏子服ID",
    System.currentTimeMillis() + 300_000,
    false, 50, "本场活动说明");
Happy.api().events().open(lease, request, settings).thenAccept(result -> {
    // 只有 result.succeeded() 才表示已提交。
});

Settings 的 null 字段在开场时使用默认值，修改时保留原值；contributionPercent 用 0–100。算法参数 contributionShare 使用 0–1，两者不要混用。

修改、结束、报名、名单和开奖提交传入 events.current() 得到的原始 Snapshot。revision 覆盖完整活动设置，不要手造快照或忽略变更冲突。

请求号为 8–64 个字母、数字或 ._:-，每个业务动作保存一个稳定编号。同编号、相同参数可重放回执；同编号改参数被拒。PENDING 表示结果待确认，用相同编号重试，不能换编号重新开奖。

开奖重试须复用原候选、原开奖结果和原 Snapshot；将它们连同请求号保存。不要以相同编号重新调用随机算法，新的结果会被当成参数冲突。

报名与名单

signup 需要玩家在配置的报名子服在线，并满足报名期限及认证要求。withdraw 同样按当前场次检查。CandidateView 包含 UUID、名字、online、eligible、排除原因、积分等级、全员轮权重和必中资格。

使用 eligible 过滤；未知资格或权重读取失败不能自行补成有效候选。名字名单的历史条目可能无法解析 UUID，RosterEntry.id 此时为 null；传送不接受未确认身份。replaceRoster 必须提供真实 UUID 和唯一的名字，不能重复 UUID 或大小写重名。

从本场移出的必中报名者不会在补抽时重新加入。长期必中规则与本场排除分别保存。

提交开奖结果

EventApi.Snapshot expected = Happy.api().events().current();
int availableSlots = Math.max(0, expected.slots() - Happy.api().events().roster().size());
Happy.api().events().candidates(expected).thenCompose(views -> {
    var pool = views.stream().filter(EventApi.CandidateView::eligible)
        .map(p -> new EventLottery.Candidate(
            p.id(), p.name(), p.contributionLevel(), p.weight(), p.guaranteed()))
        .toList();
    var result = EventLottery.draw(
        new EventLottery.Request(availableSlots, 0.5, pool), new SecureRandom());
    // 此处回到主线程再调用 submitDraw。
    return submitOnMain(lease, new EventApi.RequestContext(savedRequestId, operator),
        expected, new EventApi.DrawSubmission(pool, result, true));
});

完整可编译示例在 examples/lottery/EventWorkflowExample.java，包含切回主线程的实现。服务端重新检查报名、在线状态、认证、排除、积分等级、权重、完整候选池、轮次和名额；候选变化返回冲突，不悄悄重抽。积分轮占比必须与本场设置一致。

示例 prepareCurrentDraw 返回可保存的 PreparedDraw，submit 可使用该对象重试；drawCurrent 是首次调用的便捷入口。

首轮按“必中占总名额、积分轮、全员轮”计算；补抽只补全员轮，firstDraw=false。独立算法的必中超额会截断；原活动固定名单可超额，因此提交前应处理超额名单，不能直接假定算法结果适用于所有历史场次。

调用算法时先扣掉现有名单人数；新报名的必中仍在候选中，由算法占位。补抽用剩余名额、contributionShare=0，只补全员轮。

API 算法拒绝重复 UUID 或大小写重名。积分轮仅正积分等级参与，权重为积分等级；全员轮使用个人权重。候选不足时结果可少于名额。结果 all() 按必中、积分轮、全员轮合并。

转服回执

var expected = Happy.api().events().current();
var request = new EventApi.RequestContext(savedTransferId, operator);
Happy.api().events().transfer(lease, request, expected.id(), expected.target(), players)
    .thenAccept(receipt -> {
        // 检查每个 players() 条目的 status、attempts、message。
    });

请求先持久保存，再进入跨服队列。代理按 UUID 校验实际名字与本场名单，发起切服后记录结果；最多尝试 3 次，30 秒执行期限。未执行的旧活动/旧控制权请求取消。

SUCCEEDED 是已确认到达；PARTIAL 表示部分成功。TIMED_OUT 表示未确认，不能当作未转服。晚到的真实成功回执可以更新记录；通过 transferReceipt(savedTransferId) 查询。重试使用相同请求号，不重复发出另一批请求。

开奖日志与恢复

每次开奖先永久保存候选、原权重、各轮结果、活动版本、来源和操作者；然后以 drawId 提交名单，最后在同一事务内更新权重与完成标记。这几步不是一个跨系统事务，崩溃后按已保存决定恢复，绝不重新抽随机数。

待恢复决定会阻止下一笔开奖，避免权重先后顺序颠倒。审计库不可用时拒绝无记录开奖。框架定时恢复，缓存同步失败另行重试。历史固定名若未解析 UUID，审计有明确标记，不能把它当真实身份。
