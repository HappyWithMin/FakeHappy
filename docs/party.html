7.7 全服组队

队伍状态的权威在跨服层上，不在任何一个子服或代理的内存里 —— 网络里有多个代理、多个子服， 「队长在大厅、队员在小游戏二号服、两人还挂在不同代理下」是常态而不是边界情况。 各子服只留缓存，靠 pub/sub 失效。

跨服层不可用时 api.party().isAvailable() 是 false，查询返回空、操作返回 UNAVAILABLE， 不抛异常 —— 单机开发环境下你的游戏照常跑，只是没有跨服队伍。

小游戏要做的只有两件事，其余（队长转让、跨服带人、掉线处理）都是框架的事。

一、在 descriptor 里声明编队形态

.partyMode(PartyMode.M_BY_2)

没声明 = 组队系统认为你还没适配，party.mode 那条合规检查会报缺失。 单人游戏也要显式声明 SOLO，不是留空。

形态 规范 一支全服队伍进房间时
SOLO — 没有队的概念，各打各的（全服队伍关系仍然保留）
FOUR_BY_N 5.1 四人一队、队数不限，整体编入同一队
M_BY_N 5.2 装得下就整体编入；人数超过每队上限则队员各自选队
M_BY_2 5.3 只有两队，都装不下时拒绝进入并给明确提示
DELIVER_ONLY — 框架只送人，不编队。谁跟谁一队由你的插件决定

已经有自己一套分队逻辑的，声明 DELIVER_ONLY

子服那边多半早就有自己的分队实现了 —— 按段位排、按职业配平、按上一局结果轮换。 这些规则框架不知道，硬套 5.1/5.2/5.3 那三条只会打乱它。所以形态分两类：

你要的 声明
对接 告诉框架队伍规模，让它按规范自动编队 SOLO / FOUR_BY_N / M_BY_N / M_BY_2
不对接 只要框架把小队成员送到同一局，分队我自己来 DELIVER_ONLY

两类都会把人送过去。 「送人」是全服组队存在的意义，跟你选哪种无关：

框架照做的事 两类都一样
队长点加入 本服在线的队友一起拉进同一局
跨服排队 整支队伍占同一个房间的名额，占不下就整队换房间
队员自己点加入 挡下来，提示由队长带（规范第五章）

DELIVER_ONLY 唯一的区别是框架不给编队意见：PartyPlacement.plan 对它一律返回 INDEPENDENT，你本来就不该调它 —— 人进来之后是几队、谁跟谁，全看你自己的实现。

合规上的代价也在这里：规范 5.1「4×n 整体编入同一队」和 5.3「m×2 空位不足要拒绝」 这两条检查不再挂在你头上（框架没法验一套它不知道的规则），验收时这块改成人工看。 party.follow「队员跟随队长」和 party.leader-quit「队长退出转让」照旧要—— 人是框架送过去的，这两条躲不掉。

DELIVER_ONLY 算声明过了，party.mode 那条检查会过；留空仍然不算。

二、玩家进房间时按 PartyPlacement.plan 编队

Party party = api.party().partyOf(player).orElse(null);   // 同步读本地缓存，很便宜
int[] free = { teamA.freeSlots(), teamB.freeSlots() };     // 下标就是队伍编号

PartyPlacement plan = PartyPlacement.plan(
        party == null ? 0 : party.size(), descriptor.partyMode(), TEAM_CAP, free);

switch (plan.decision()) {
    case TOGETHER    -> putWholeParty(party, plan.teamIndex());
    case INDEPENDENT -> putAlone(player);          // 这一局不同队，但队伍关系保留
    case DENIED      -> {
        text.sendPrefixed(player, plan.reason());  // 原样展示，别自己另写一句
        // denyOptions() 是「解散全服队伍后单独加入」/「更换其它房间」，做成两个按钮
        for (String opt : PartyPlacement.denyOptions()) offer(player, opt);
    }
}

plan 是纯函数，你照结果执行就行。

DENIED 时展示 reason() 并提供 denyOptions() 两个选项，符合规范 5.3。

剩下的都不用你管

事情 谁做
队长退出 → 转让给在线时长最长的队员（5.4） 框架。切子服不重置在线时长
队员跟随队长跨子服（warp） 框架 + 代理。队长先过去，队员随后
跨服排队 队长点「加入」时整队分到同一个房间；队员自己点会被挡下，提示由队长带
掉线 有意不散队。网络抖一下不该把人踢出队伍；全员离线 30 分钟后队伍键自己过期
邀请超时 60 秒，过期后 accept 返回 INVITE_EXPIRED
玩家命令 /party invite|accept|deny|leave|kick|promote|disband|warp|list（别名 /p /team）

队伍上限默认 4 人，改 modules.party.max-size。

要自己判断「队伍里现在有几个人真的在线」，用 api.party().onlineMembers(partyId) —— 它按心跳判，不是按本机 Bukkit.getPlayer 判。队友本来就多半在别的子服上， 按本机在线判会把他们全算成离线。代价是刚上线的成员最多晚一个心跳周期（15 秒）才算进来。

别的子服上的队友，框架不替你安置

队长在本服点加入时，框架把本服在线的队友一起拉进同一局。别的子服上的队友 不会被自动送过来 —— 要把他们放进队长所在的那一局，得先知道队长落在哪个房间， 而只有你的游戏知道。框架不猜，但会告诉队长「有 N 名队友在别的子服上」， 不会让他以为人都跟过来了。

想让他们跟过来，两条现成的路：

  • 队长先 /party warp <子服> 把人叫过来，再一起点加入
  • 或者由你的游戏自己调 api.network() 那套接口去安排 —— 你知道该塞进哪一局

本服没有这个游戏时不存在这个问题：那条路走跨服排队，整支队伍由代理分到同一个房间。

结果文案不用你写

PartyResult 每一项都自带一句给玩家看的话：

api.party().invite(a, b).thenAccept(r -> {
    // 回调在异步线程！碰 Bukkit 对象要自己切回主线程
    text.sendPrefixed(player, r.message());   // "对方已经在别的队伍里了" ……
});

各处的说法就此统一。查询（partyOf / isLeader / pendingInviteFrom）是同步的、 读本地缓存，事件处理里可以直接调；写操作全部返回 CompletableFuture。
